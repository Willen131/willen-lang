# 测试集有效性验证

日期：2026-10-16

**要回答的问题**：12 个模块、247 个断言的黑盒测试集，**它本身可靠吗？**

测试集全绿只能说明「当前实现与我的期望一致」，不能说明「测试集能发现缺陷」。
如果一个测试集写得足够宽松，任何错误实现都能通过它。

验证手段是**变异测试**：在解释器源码里注入小缺陷，看测试集能否抓住。

---

## 1. 方法与工具

`tools/mutation_test.py` 自动完成以下流程：

1. 确认工作区干净（保证中断后可用 `git checkout` 恢复）
2. 确认基线是绿的（否则变异测试没有意义）
3. 对每个变异体：注入缺陷 → 编译 → 跑测试集 → 记录结果 → **立即还原**
4. 输出杀死率与明细

判定标准：

| 结果 | 含义 |
|---|---|
| **被杀死** | 测试集失败 → 缺陷被发现 |
| **被杀死（超时）** | 测试 30 秒未结束，疑似死循环 → 同样算被发现 |
| **存活** | 测试集仍然全绿 → **测试集漏掉了这类缺陷** |

超时之所以算「被杀死」，是因为某些变异会让程序死循环而不是给出错误结果——
例如「加法改成减法」之后，测试里 `当 (计数 < 5) { 计数 = 计数 + 1 }`
这类循环永远不会结束。这类缺陷显然也是被发现的。

复现方式：

```bash
python tools/mutation_test.py
```

## 3. 过程中的两次假结果

**必须记下来，因为它们说明「工具本身也需要被验证」。**

### 假结果一：10/10，全部「编译失败」

前两次运行，脚本报告 10 个变异体全部被杀死，但理由都是**编译失败**。

手动编译明明是成功的——顺着这条线索查下去，发现真正的原因：

```
Assembler messages:
Fatal error: can't create C:\Users\willen\Documents\?...\.build-tmp\ccFH6nkV.o
```

**汇编器无法在临时目录里创建目标文件，而且报错路径里的中文是乱码。**

根因是 `build.sh` 里的 `BUILD_TMP="$PWD/.build-tmp"`：从交互式 Git Bash 运行时
`$PWD` 是正确的 UTF-8，一切正常；但**从 Python 的 subprocess 调用时，
环境里继承的 `PWD` 编码已被破坏**，MinGW 的 g++ 又是通过 ANSI 接口读工作目录，
中文路径一转换就成了乱码。

修法：临时目录改用 `$USERPROFILE`（`C:\Users\willen`，纯 ASCII）下的专用目录。

**如果当时采信了那个「100%」，就会把一份假证据写进交付物——测试集实际从未被检验过。**

### 假结果二：第一次真实运行得到 9/10

修好构建后，第一次真实结果是 **9/10**：变异体 4（数组越界检查放宽一格）**存活**。

这不是工具的问题，而是测试集的真实盲区——见下一节。

---

## 4. 真实发现：一个测试盲区

**变异体 4**：把 `if (i < 0 || i >= n)` 改成 `if (i < 0 || i > n)`。
效果是允许下标等于长度，也就是**只越界一个位置**。

**为什么没抓住？** 因为原有的越界测试用例是：

```willen
设 甲 = [1, 2, 3]
打印(甲[10])      # 长度 3，下标 10 —— 远越界
```

`10 > 3` 依然成立，所以变异后仍然报错。**远越界无法暴露「放宽一格」的缺陷。**

补上的用例：

```willen
设 甲 = [1, 2, 3]
打印(甲[3])      # 下标正好等于长度 —— 第一个越界位置
```

验证：未变异时该用例通过（报错信息与期望一致）；注入变异后测试集失败（变异被杀死）。

**这个盲区值得强调**：它属于测试设计的经典问题——**只测「明显越界」不够，
必须测「刚好越界的那一个位置」**。

而且它有现实后果：如果老师答辩时随手试一下 `甲[3]`，在未修正的实现上会读到
越界内存。变异测试在交付前就把这个洞补上了。

## 5. 最终结果

| 指标 | 值 |
|---|---|
| 变异体总数 | 10 |
| 被杀死 | 10 |
| 存活 | 0 |
| **杀死率** | **10/10 = 100%** |

| 变异体 | 结果 | 被哪个测试抓住 |
|---|---|---|
| 1 加法改减法 | 被杀死（超时） | 大量循环用例陷入死循环 |
| 2 除法改取模 | 被杀死（超时） | 同上 |
| 3 比较边界 | 被杀死 | `02_运算符` 的比较用例 |
| 4 越界放宽一格 | 被杀死 | **`12_错误处理_数组越界边界`（本次新增）** |
| 5 字符串长度 | 被杀死 | `03_字符串` |
| 6 切片边界 | 被杀死 | `04_数组` |
| 7 排序反向 | 被杀死 | `04_数组` |
| 8 真值判断 | 被杀死 | `06_分支` |
| 9 常量检查 | 被杀死 | `12_错误处理_常量重赋值` |
| 10 递归上限 | 被杀死 | `12_错误处理_递归过深` |

明细数据见 `docs/变异测试结果.csv`。

补充边界用例后，**断言总数不变**（仍是 247 个）——
新增的是错误处理用例，它期望脚本**失败**，不计入断言数。
错误处理用例从 8 个增加到 **9 个**，测试文件总数从 19 个增加到 **20 个**。

---

## 6. 结论

1. **测试集有效**：10 个覆盖六类缺陷的变异体全部被抓住，杀死率 100%。

2. **但「100%」这个数字是补了一个洞之后才拿到的。** 第一次真实运行是 9/10，
   存活的那个变异暴露了「只测远越界、不测边界值」的盲区。
   **如果只看测试集全绿就交付，这个洞会一直存在。**

3. **工具本身也需要被验证。** 变异测试的前两次运行给出了 10/10 的假结果，
   原因是构建脚本在程序化调用下会失败。**结果的「完美」本身就是需要警惕的信号。**

4. **本项目里「中文路径」已经第三次成为问题源**（另两次见 CHANGELOG 的 Day 8 与
   Day 17 附近）。这不是巧合——它反复出现在「手动跑没问题、程序化调用出问题」
   这个模式里。
