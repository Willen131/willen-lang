# 现场演示脚本

目标：在 4 分钟内展示 Willen 语言的核心能力，并留出足够时间应对提问。

**两条原则：每一条命令都提前跑通；每个环节都准备截图备份。**

---

## 演示前检查清单（提前 10 分钟）

- [ ] `bash build.sh` 已执行，`willen.exe` 存在
- [ ] 终端字体支持中文与 `█` `·` 等符号
- [ ] 终端窗口足够大（**至少 100 列 × 32 行**，迷宫有 25 列宽）
- [ ] `./willen test tests/` 能跑通
- [ ] `./willen run apps/迷宫.wl` 输出对齐正常
- [ ] 所有环节的截图已备好（同一文件夹，按顺序命名 `01-测试集.png` 等）
- [ ] 关闭无关窗口与通知

**关于终端**：`willen.exe` 启动时会调用 `SetConsoleOutputCP(CP_UTF8)` 设置
控制台编码，正常情况下中文不会乱码。若仍有问题，改用 Windows Terminal。

**关于迷宫对齐**：`█` 是东亚宽度字符，`·` 是半角。在过窄的终端里，
起点行与终点行（含汉字标记）会比其它行多占一列，属显示层问题，
不影响逻辑。演示前务必用实际终端确认一次。

## 演示流程

### 0:00 – 0:30　开场：语言长什么样

**做什么**：打开 `apps/迷宫.wl` 开头，让观众先看到源代码。

```willen
函数 取随机(上界) {
    随机状态 = (随机状态 * 1103515245 + 12345) % 2147483648
    设 结果 = (随机状态 / 65536) % 上界
    返回 结果
}
```

**讲什么**：

> "这是 Willen 语言——中文关键字的类 C 脚本语言。
> `设` 是变量声明，`函数` 定义函数，`返回` 返回值。
>
> 中文关键字不是简单地把英文替换掉：UTF-8 里每个汉字编码成 3 个字节，
> 只要把标识符的判定规则放宽到接受非 ASCII 字节，
> 中文就能像英文一样做标识符——**本质是「规则放宽 + 一张哈希表」，不需要任何特殊处理**。"

**要点**：这 30 秒就把最核心的实现原理讲清楚了，也为后面的提问埋好伏笔。

---

### 0:30 – 1:30　解释器：一条命令跑完所有测试

**命令**：

```bash
./willen test tests/
```

**预期输出**：

```
[通过] 01_字面量与类型.wl
[通过] 02_运算符.wl
[通过] 03_字符串.wl
...
[通过] 12_错误处理_递归过深.wl（预期出错）
--------------------------------
共 19 个测试文件，通过 19，失败 0（另有 6 个 .wl 无 .expected，已跳过）
```

**讲什么**：

> "12 个模块、247 个断言，一条命令跑完。
>
> 测试脚本全部用 Willen 语言自己写——包括这个断言库，
> 也就是说**测试基础设施是被测试的语言自己实现的**。
>
> 最后 8 个是错误处理用例：它们期望脚本**失败**，
> 比对的是标准错误里的中文错误信息。所以连报错的行号和措辞都被测试覆盖了。"

**如果老师追问「怎么保证测试有效」**：

> "期望文件全部手写，不用解释器生成——自动生成的期望只是把当前行为抄了一遍，
> 无论对错都会通过。而且**真的抓到过**：Day 10 我手写期望时把 23 个数成了 20，
> 是这个机制把差异报出来的。"

### 1:30 – 2:30　应用：Agent 写的迷宫

**命令**：

```bash
./willen run apps/迷宫.wl
```

**预期输出**（约 30 行）：

```
──────────────────────────────────
迷宫统计
──────────────────────────────────
单元格规模：12 × 12
网格边长：25 × 25
通路格数：287
最短路径长度：145 格
──────────────────────────────────

█████████████████████████
█起····█     █         █ █
█████·█████ █ ███ ███ █ █
█ █···█···█   █   █     █
...
█       █  ·····█·····█终█
█████████████████████████
```

**讲什么**：

> "这个迷宫程序 **321 行，完全用 Willen 语言写的**，
> 而且是用编程 Agent 开发的——我只给它一份语言指南，
> **禁止它读取项目里的任何其他文件**。
>
> 功能包括：递归回溯生成迷宫、广度优先搜索求最短路、
> 字符画渲染（墙、通路、路径、起终点）、统计信息，
> 还有第二种渲染模式——只看路径的形状。
>
> 路径从「起」连续贯通到「终」。"

**时间够的话**，再跑一次展示第二种渲染模式（只看路径）。

### 2:30 – 3:30　性能：从 64 倍到 4 倍

**打开**：`docs/性能测试报告.md` 第 3 节的结果表。

**讲什么**：

> "性能上做了两轮优化。
>
> **第一轮是变量槽位化**：原来每次变量访问都要在哈希表上做字符串比较，
> 改成在解析期把局部变量绑定成下标，运行期直接按数组下标寻址。
>
> **第二轮是求值分发**：原来用一长串 `dynamic_cast` 判断节点类型，
> 每求值一个节点要尝试十几个类型；改成枚举加 `switch` 后只剩一次跳转。"

**指着表格讲**：

> "`sort` 从 13.4 秒降到 0.94 秒，**快了 14 倍**。
> 相对 CPython 的倍率从 8.6–64.5 倍收敛到 **2.0–9.9 倍**。"

**最有价值的一句**：

> "做完第一轮优化，`fib` 只快了 8%。
> **正是这个「低于预期」的信号**让我去查真正的热点，
> 才发现 `dynamic_cast` 才是大头，随后拿到 5 到 8 倍的提升。
> 如果我当时因为'优化已经有效果了'而收手，就会错过它。"

**如果老师问「为什么还是比 Python 慢」**：

> "要分负载看：数值循环密集的负载已经追到 **2 倍**；
> 函数调用密集的 `fib` 还差 **9.9 倍**——因为 Willen 每次调用都要新建帧，
> 而 CPython 的帧是复用的。**这是报告里写明的最大短板**，
> 也是我给出的后续优化方向。"

### 3:30 – 4:00　AI 指南：怎么让 Agent 一次写对

**打开**：`skills/willen/SKILL.md` 第一节「硬性规则」。

**讲什么**：

> "这份指南的第一节是「硬性规则」，八条。
> 其中大部分不是凭空想的，是**实际踩过的坑**：
> 条件漏括号、字符串里的花括号、浮点打印。"

**关键的一句**：

> "我做了一次**对照实验**：同样的 Agent、同样的任务，
> **唯一的变量是指南内容**。
>
> 第一轮它写出了能跑的代码，但绕了远路——
> 因为指南没写「函数能不能改顶层变量」，
> 它就用一个单元素数组当「可变盒子」来传状态。
> 我把这条补进指南后，第三轮它直接用顶层变量了。
>
> **这证明指南的修订是真的有效，而不是'我改了文档'而已。**"
