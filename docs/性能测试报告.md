日期：2026-10-14

---

## 2. 测试方法

### 2.1 基准设计

五组基准，每组都有功能等价的 Willen 与 Python 两个版本：

| 基准 | 内容 | 考察点 |
|---|---|---|
| `fib` | 递归 `fib(27)` | 函数调用开销 |
| `loop` | 累加 1…1,000,000 | 循环与变量读写 |
| `sort` | 冒泡排序 2000 个元素 | 数组下标读写 |
| `str` | 10 万次字符串拼接 | 字符串分配与拷贝 |
| `maze` | 40×40 迷宫生成 + BFS 求解 | 综合场景 |

### 2.2 公平性保障

**这是本报告最需要说明的部分。** 两语言性能对比很容易做成不公平的，
以下是逐条的保障措施：

**① 算法完全一致**
两语言版本的循环结构、执行顺序、变量职责逐行对应。不存在「一边调用内置
排序、一边手写冒泡」这类对比。

**② 输入数据完全一致**
`sort` 与 `maze` 依赖伪随机序列。两语言使用**同一个自己实现的线性同余
生成器**（相同的乘数、增量、模数与种子），不依赖任何语言的内置随机数。
因此排序的是同一组数字、生成的是同一座迷宫。

**③ 结果可校验**
每组基准都输出确定的结果值，只有两语言**逐字节比对一致**才计入成绩。
这排除了「一边真算了、一边少算了」的可能。

**④ 多次测量取中位数**
每组运行 3 次取中位数，降低系统噪声与偶发抖动的影响。

**⑤ 计时在进程外部**
用 Python 的 `perf_counter` 从外面计时，不依赖任何语言自身的计时函数——
否则计时的实现差异会混进结果。

**⑥ 同一台机器、连续测量**
所有数据在同一次会话内连续采集，避免环境漂移。

### 2.3 一个测量过程中发现的细节

Willen 输出 LF 换行，而 Python 在 Windows 上输出 CRLF。首轮自动比对时，
单行输出的基准靠 `strip()` 掩盖了差异，**多行输出的 `sort` 与 `maze` 却被
误判为「两语言结果不一致」**。用 `od -c` 逐字节查看才发现是行尾问题。

测量脚本已在比对前统一行尾。**这件事说明自动化比对本身也需要被验证**——
当时若不手工复核，就会去查一个根本不存在的语言缺陷。

## 3. 测试结果

优化分两步（见第 4 节），因此有三组数据。

### 3.1 完整结果表

| 基准 | v1 基线 | v2 槽位化 | v3 +kind分发 | Python | v3 / CPython |
|---|---:|---:|---:|---:|---:|
| `fib` | 0.906 | 0.840 | **0.318** | 0.032 | 9.9× |
| `loop` | 1.693 | 1.491 | **0.205** | 0.092 | 2.2× |
| `sort` | 13.375 | 7.635 | **0.938** | 0.231 | 4.1× |
| `str` | 0.835 | 0.842 | 0.727 | 0.097 | 7.5× |
| `maze` | 0.254 | 0.239 | **0.044** | 0.023 | 2.0× |

（单位：秒，均为 3 次中位数）

### 3.2 优化幅度

| 基准 | v1 → v3 提升 | 相对 CPython 倍率的收敛 |
|---|---:|---|
| `fib` | 2.9× | 27.6× → **9.9×** |
| `loop` | 8.3× | 17.2× → **2.2×** |
| `sort` | **14.3×** | 64.5× → **4.1×** |
| `str` | 1.1× | 8.6× → 7.5× |
| `maze` | 5.8× | 11.0× → **2.0×** |

**两轮优化把相对 CPython 的倍率从 8.6–64.5 倍收敛到 2.0–9.9 倍。**

---

## 4. 优化过程与归因

### 4.1 优化一：变量槽位化（v1 → v2）

**原实现**：每次变量访问都要在 `unordered_map<string, Value>` 上做一次
字符串哈希与比较。

**改法**：新增 `Resolver`，在解析期扫描语法树，把函数内的局部变量
（含参数、遍历的循环变量）绑定成槽位下标；运行期按 `vector` 下标直接寻址。
全局变量不分配槽位——数量少，哈希开销可忽略。

顺带得到一个简化：**作用域链整个消失了**。块级作用域在解析期就处理完毕
（同名变量在不同块里分到不同槽位），运行期不再需要创建与销毁作用域对象。

**效果**：`sort` 提升 1.75×，其余基准提升有限。

**归因**：`sort` 的每轮内层迭代要访问两次变量（数组名与下标名）再加两次
数组下标，变量查找在总开销里占比最高。而 `fib` 的开销在函数调用、
`str` 在字符串复制，变量查找都不是主要成本——所以它们没怎么变快。

### 4.2 优化二：求值分发改用 kind 枚举（v2 → v3）

**原实现**：`eval` 用一长串 `dynamic_cast` 判断节点类型，**每求值一个节点
都要逐个尝试十几个类型**。`dynamic_cast` 需要查询运行时类型信息，比一次
跳转慢得多；而 `eval` 是**递归调用**的（每个子表达式都要重新分发），
这个开销被成倍放大。

**改法**：给 `Expr` 加 `ExprKind` 枚举字段，各节点构造函数填入自己的种类；
`eval` 改用 `switch` 分发，只剩一次跳转加一次 `static_cast`。

**效果远超预期**：

| 基准 | v2 → v3 |
|---|---:|
| `loop` | 1.491 → 0.205（**7.3×**） |
| `sort` | 7.635 → 0.938（**8.1×**） |
| `maze` | 0.239 → 0.044（**5.4×**） |
| `fib` | 0.840 → 0.318（2.6×） |

**这条值得单独记下来**：最初做槽位化时，我以为变量查找是最大瓶颈；
做完却发现 `fib` 只快了 8%。**正是这个「低于预期」的信号**，
促使我去查真正的热点，才发现了 `dynamic_cast` 分发的问题。

**如果当时因为「优化已经有效果了」而收手，就会错过这个 5–8 倍的提升。**

### 4.3 唯一没有改善的一项

`str` 从 8.6× 只降到 7.5×，几乎没有变化。

**原因**：它的热点是**字符串复制**。`文本 = 文本 + "x"` 每轮都要把已有的
全部内容复制一遍，算法本身是 O(n²)。这既不是变量查找问题，也不是节点
分发问题，两次优化自然都帮不上。

**这一项恰好印证了优化是有的放矢的**——如果所有基准都均匀提升，
反而要怀疑测量方法出了问题。

## 5. 与 CPython 的差距分析

v3 相对 CPython 的倍率落在 2.0× 到 9.9× 之间。差距来自哪里：

### 5.1 Willen 的劣势

| 因素 | 说明 |
|---|---|
| **AST 树遍历 vs 字节码** | Willen 每执行一个节点都要在树上游走一次；CPython 先编译成字节码，执行时是扁平的指令序列，缓存局部性更好 |
| **函数调用开销** | Willen 每次调用要新建一个 `vector<Value>` 帧并 `assign` 出全部槽位；CPython 的帧是预分配复用的 |
| **值类型宽度** | Willen 的 `Value` 是 `variant`，含一个 `shared_ptr` 的宽度；CPython 的 `PyObject*` 是指针宽度 |
| **每节点带虚析构** | `Expr` 有虚析构函数，节点比纯数据略大 |

### 5.2 Willen 的优势

| 因素 | 说明 |
|---|---|
| **算术是静态分派的** | 命中 `variant` 的整数分支后直接做 `int64` 运算；CPython 每次算术都要走 `PyNumber_Add` 通用协议 |
| **无引用计数风暴** | Willen 用 `shared_ptr`，但没有 CPython 那样每次操作都增减引用计数的开销 |
| **变量槽位在解析期定好** | 全局与属性查找也省掉了字典查询 |

### 5.3 为什么 `loop` 与 `maze` 能追到 2 倍

这两个基准的热点是**纯数值循环**：整数加减、比较、数组下标。这类操作
Willen 用原生 `int64` 直接算，而 CPython 每个整数都是一次对象操作。
因此在这类负载上，差距被压缩到 2 倍左右。

### 5.4 为什么 `fib` 仍差 9.9 倍

`fib(27)` 需要约 60 万次函数调用，且绝大多数是「调用 + 比较 + 返回」
的极短函数。Willen 每次调用要：

1. 为实参构造一个 `vector<Value>`
2. `assign` 出整个帧（`slotCount` 个默认构造的 `Value`）
3. 执行函数体
4. 恢复旧帧

CPython 的帧是复用的，没有前两步的分配成本。

**函数调用是当前最大的性能短板**，若要继续优化，应从这里入手。

---

## 6. 结论

1. **两轮优化把相对 CPython 的倍率从 8.6–64.5 倍收敛到 2.0–9.9 倍。**
   `sort` 一项提升 14.3 倍。

2. **最大的收益来自一次「低于预期」的信号。** 槽位化后 `fib` 只快 8%，
   顺着这个线索才找到 `dynamic_cast` 分发这个真正的热点。
   **优化必须由测量驱动，不能靠猜。**

3. **性能差异高度依赖负载类型**：数值循环密集的负载上 Willen 已接近
   CPython（2.0–2.2 倍）；函数调用密集或字符串复制密集的负载上差距仍大
   （7.5–9.9 倍）。**笼统地说「快」或「慢」没有意义，必须分负载讨论。**

4. **已知的最大短板是函数调用**（每次新建帧）。这是后续最值得优化的方向。

5. **所有数据可复现**：`python bench/run_bench.py` 一条命令重跑五组基准，
   自动校验两语言结果一致，并输出 CSV 与 Markdown 表格。
